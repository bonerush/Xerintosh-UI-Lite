# Debug 记忆自动整理规则

> 本规则定义 debug 活动结束后，如何自动提取教训并保存为持久化记忆。
> 目标：让每一次 debug 的踩坑经验都能沉淀下来，避免重复踩坑。

---

## 1. 触发条件：何时整理

以下任一信号出现，即视为当前 debug 活动结束，**必须**执行记忆整理：

| 信号类型 | 示例 |
|---------|------|
| 用户明确结束 | "bug 修好了"、"问题解决了"、"debug 结束"、"先这样吧" |
| 验证通过 | 用户发送截图确认修复生效、说"可以了"、"没问题了" |
| 发现根因并修复 | 已经定位 root cause 并实施修复，无论是否完全验证 |
| 放弃当前方案 | 用户决定换一种方案、回滚修改、或标记为"暂时不管" |
| 长时间无进展 | 同一问题排查超过 30 分钟无明显进展，应记录已排除的方向 |

**例外情况**（不整理）：
- 纯粹的语法错误、拼写错误（除非反复出现同一种）
- 已经记录在现有 memory 中的完全相同的问题
- 临时调试代码（如加了一行 `printf` 查看变量值）

---

## 2. 整理流程：四步法

### Step 1: 提取核心教训

从本次 debug 对话中提炼以下要素：

```
症状（Symptom）: 最初观察到的异常现象，用户原话优先
根因（Root Cause）: 导致问题的根本原因，而非表面现象
修复（Fix）: 具体的代码修改、配置调整或操作步骤
为什么（Why）: 这个修复为什么有效，底层机制是什么
如何预防（Prevention）: 未来避免同类问题的方法或检查清单
相关文件（Files）: 涉及修改的关键文件路径
```

**提取原则**：
- 一个 debug 会话可能产生**多条**独立教训，每条单独记录
- 优先记录"反直觉"的陷阱（如"ESP32 未初始化变量是随机值而非 0"）
- 保留具体的错误信息、返回值、错误码（如 `LoadStoreError`、`-2`）

### Step 2: 去重检查

写入前，先搜索现有 memory 文件，确认该教训是否已存在：

```bash
# 检查 memory 目录下是否已有相似内容
grep -r "<关键词>" ~/.claude/projects/<project>/memory/
```

若已存在，评估是否需要：
- **补充**：在现有条目下增加新的场景或细节
- **跳过**：完全重复，无需记录
- **新建**：虽然主题相似，但属于不同场景

### Step 3: 写入 Memory 文件

将教训写入项目的 memory 目录：

**文件路径**：
```
~/.claude/projects/<project-name>/memory/feedback_<topic>.md
```

- `<topic>` 用简洁的英文或拼音描述主题（如 `wifi_scan`、`u8g2_datum`、`slider_overflow`）
- 同一主题的多个教训可以追加到同一个文件，用 `---` 分隔
- 不同主题的教训应分文件存放

**文件格式**：

```markdown
---
name: <简短的教训标题（20字以内）>
description: <一句话概括核心教训>
type: feedback
---

## <具体教训标题>

<详细描述问题现象和解决过程>

**Why:** <为什么发生，底层机制>

**How to apply:** <如何预防、应用或检查>

---

## <第二条教训（如有）>

...
```

### Step 4: 更新索引

修改同目录下的 `MEMORY.md`，在 Feedback 区域添加新记忆的链接：

```markdown
## Feedback
- [嵌入式 UI 开发经验教训](feedback_embedded_ui.md) — ...
- [新主题](feedback_<topic>.md) — <一句话描述>
```

---

## 3. 内容质量要求

### 必须包含

- **具体的错误现象**：不是"出错了"，而是"屏幕黑屏并自动重启"
- **具体的修复代码**：提供修改前后的代码对比（WRONG / CORRECT）
- **底层原因**：不是"改好了"，而是"栈变量指针悬空导致 LoadStoreError"
- **可操作建议**：读者看到这个记忆后能立即知道怎么避免

### 避免记录

- 过于个人化的调试步骤（如"我先把线拔了再插上"）
- 未验证的猜测（用"可能"、"也许"开头的推断）
- 纯框架/库的使用文档（应引用官方文档链接，而非复制）
- 临时性 workaround（除非确认为长期方案）

## 4. 自动化机制

### 首选：会话结束时自动检查

在 `~/.claude/settings.json` 中配置 Stop Hook，在会话结束时触发记忆整理检查：

```json
{
  "hooks": {
    "Stop": [
      {
        "command": "echo '[Debug Memory] 会话结束，如涉及 debug 请运行 /dream 整理记忆'",
        "description": "提醒整理 debug 记忆"
      }
    ]
  }
}
```

### 备选：手动触发

在任意时刻，用户可以主动说"整理 debug 记忆"或运行 `/dream` 命令，触发完整的记忆整理流程。

### 自动检测启发式

Claude 在会话中自动检测以下 debug 信号：
- 用户提到 "bug"、"报错"、"崩溃"、"黑屏"、"乱码"、"重启"
- 出现代码 diff（修改源代码）
- 出现编译错误、运行时错误信息
- 用户发送截图验证修复效果
- 讨论涉及 "为什么"、"root cause"、"根因"

当检测到这些信号时，Claude 应在会话结束前主动提示："本次会话涉及 debug 活动，是否整理到记忆？" 或**直接执行整理**（在 Auto Mode 下）。

---

## 5. 记忆使用

### 新会话开始时

启动新会话后，Claude 应：
1. 读取 `MEMORY.md` 了解已有记忆
2. 当用户提出新问题时，优先搜索相关 memory
3. 若发现用户可能正在踩已记录的坑，主动提醒："根据之前的记忆，这个问题可能是..."

### 排查问题时

当用户报告问题时，Claude 应：
1. 在 memory 中搜索相似症状
2. 先验证已知的常见原因，再探索新方向
3. 如果排查方向与已有记忆冲突，优先质疑新假设

---

## 6. 维护与清理

### 定期回顾

每完成 3-5 个新记忆或每隔 2 周，执行一次记忆整理：
- 合并相似主题的条目
- 删除已过时或不再适用的记忆
- 更新 `MEMORY.md` 确保链接有效
- 检查源文件路径和行号是否仍然准确

### 使用 `/dream`

运行 `/dream` 命令可以自动执行上述维护工作，包括：
- 合并重复的记忆
- 更新 MEMORY.md 索引
- 清理无效链接
- 优化描述的清晰度
